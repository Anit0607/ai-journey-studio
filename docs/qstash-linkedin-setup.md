## Exact minimum schedule proposal

Use the verified owner's **QStash Free** account and its observed regional API base. Do not assume the account exists, is on Free, or has unused capacity. The canonical application origin is `https://ai-journey-studio.vercel.app`.

Set no delay, callback, failure callback, content-based deduplication, forwarded bearer credential, source text or publication instructions. QStash supplies its own signature. The app rejects nonempty JSON, wrong URL/query/host, missing/invalid signatures, and unsupported request encoding.

The schedule-management operation is `POST {verified-QStash-base}/v2/schedules/{full-destination}` with `Upstash-Schedule-Id`, `Upstash-Cron`, `Upstash-Method: POST`, `Upstash-Timeout`, and **explicit `Upstash-Retries: 0`**. An omitted retry value defaults to three retries. Existing schedule IDs are updated by this API, so list first and do not overwrite an unrelated schedule. Prefer the authenticated provider console when it exposes every required field; the app itself needs no QStash administration token. See [create schedule](https://upstash.com/docs/qstash/api-reference/schedules/create-a-schedule).

### Capacity and cost boundary

- Two-minute intake/publication means 720 planned deliveries/day; the daily batch adds one. Total: **721/day**, leaving 279 of the published 1,000/day allowance for existing account traffic, duplicates and deliberate tests. These are planned deliveries, not a provider-enforced hard bound.
- Require two available slots within the published ten-active-schedule Free limit. Inspect all existing account schedules and recent usage, not just this app. Do not enable if shared traffic removes safe headroom.
- Proposed additional scheduler spending limit: **US$0**. No card entry, paid upgrade, automatic upgrade, paid add-on or overage authorization. If Free is unavailable or account terms differ, stop and ask. Vercel, database and model charges are separate; this scheduler limit does not cap them.
- Every retry is an additional counted message. Zero retries preserves the planned allowance; it does not turn QStash's at-least-once delivery into exactly-once delivery. The provider describes quotas as soft limits, so do not claim an automatic hard spending cutoff. See [QStash pricing](https://upstash.com/pricing/qstash).

### Timing and failure semantics

The app allows 300 seconds of publication lateness. Five-minute polling leaves no useful latency margin and must not be used for this plan. The two-minute schedule leaves nominal margin for the integration tick's 150-second deadline; the deployed route has a 180-second maximum. A slow prior invocation, the 240-second durable tick lease, source sync, database delays, provider delays or an outage can still cause a missed window. This is approximate delivery, not an exact-time guarantee. Initially schedule at most one LinkedIn post in any ten-minute interval and verify real latency before relying on it.

Only one due publication is considered per tick. Missed/invalidated earlier items may consume a tick too. Before a real publication, inspect the outbox for blocked or overdue items and do not silently delete or reschedule them. A missed window requires an explicitly revised, newly approved time. An uncertain provider outcome requires receipt reconciliation, never automatic replay.

With `retries=0`, QStash does not retry a failed transport delivery. The next two-minute schedule event is a new wake, not a retry of a LinkedIn post. A failed daily event waits for the next daily event unless the owner separately authorizes a safe recovery after inspecting the persisted batch state. Once a UTC-day batch row exists, another event cannot run that day again, including after failure. Never delete the row to force a retry. See [retry semantics](https://upstash.com/docs/qstash/features/retry).

## Hourly GitHub polling: code-backed rate calculation

`source_interval_minutes=60` gates source work inside the frequent integration tick; it does not add another QStash schedule. After a normally completed tick, `next_source_sync` is set to tick-start plus one hour, including a returned blocked/partial/failed source result. Initial activation can sync immediately. Intake only stages evidence; the independent daily generation route dispatches eligible sources.

For the single allowed repository, a commit-only sync performs at most one repository GET and two commit-page GETs: **three content reads**. With up to five exact notes, the cap is **12 read attempts**: repository 1 + commit pages 2 + optional immutable commit resolution 1 + nonrecursive trees 3 + Contents files 5. The GitHub App resolver adds one installation GET and one token-creation POST when obtaining its short-lived token; these are not included in `github_read_counts`. The resolver is newly constructed per integration invocation, so do not assume a cross-invocation token cache.

With a fresh installation token remaining outside its one-minute refresh margin throughout each sync, the normal plan is **120 total GitHub requests/day for commit-only** or **336/day with notes**, including both App authentication requests per sync. The normal per-hour envelope is 5 or 14. This is not an unconditional auth-request bound: the resolver accepts shorter-lived tokens and may obtain a new one before another content read. A conservative code-path envelope allows two authentication requests per content read: 9 total requests per commit-only sync or 36 with notes, hence 216 or 864 requests/day at hourly cadence. Because `next_source_sync` advances only after sync returns and its database update succeeds, a crash/storage failure can make a later two-minute wake attempt sync again. If every scheduled tick syncs, the normal fresh-token calculation is 150 or 420 requests/hour; allowing authentication before every content read gives 270 or 1,080 requests/hour. Both exclude provider duplicates, owner-triggered syncs and other account traffic. These are not independent hard daily usage caps. A failed credential acquisition can also be attempted again on later wakes.

GitHub documents a minimum 5,000 requests/hour for installation-token API requests, but app-auth and secondary/shared limits must still be checked from the actual account and sanitized rate-limit headers. Rate/access errors must remain visible; do not bypass them or claim guaranteed quota availability. [GitHub rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api). Code references: `lib/integrations.ts`, `lib/source-ingestion.ts`, `lib/github-app-auth.ts`, `GITHUB_BUILD_NOTES.md`.

## Replay safety: what the code does and does not prove

`lib/qstash-scheduler.ts` verifies the raw body, HS256 signature with current/next keys, issuer, exact destination, time claims and authenticated JWT `jti` before opening the database. `(destination, signed_jti)` is durably claimed and never replayed, even after a crash. Unsigned message/schedule headers are not trusted as identity.

New signed events still pass the durable integration lease and source cursor/dedup gates. Publication locks the exact approved outbox version, records its claim and request attempt, rechecks source/account/content/time approval immediately before sending, and never requeues claimed/failed/uncertain outcomes automatically. The daily route keeps its separate one-attempt-per-UTC-day guard, safe checkpoint persistence and unresolved-accounting stop. These are code-backed protections, not proof of actual live delivery or exactly-once behavior in an external provider. Relevant tests are `tests/qstash-scheduler.test.ts`, hosted-batch, source-ingestion and publishing suites; this docs change runs no paid or live tests.
