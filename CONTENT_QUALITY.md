# Practical-journey editorial review

Factual admissibility and worthwhile content are separate. A zero-grounding-flags
result is not proof of a useful story, natural voice or fit with the owner's brief.

The runtime brief is for people already using ChatGPT/Codex who want practical
methods for building and directing agents. Select one evidenced problem or
constraint, a documented choice/instruction/experiment/change, the agent/system
action, and its observed result or honest limit. Show the practical method through
that episode rather than reciting a build log or generic beginner advice.

Human texture may come from specific choices, friction and tradeoffs. Feelings,
quotes, owner actions, first-person experience, success and causal claims must
still come from the currently cleared source. Source permissions are unchanged;
no private chat is imported or sent by this correction. A repository note can
support an attributed practical episode without establishing the owner's emotions
or personal discovery. A title-only or otherwise insufficient source should yield
an internal hold, not a calendar-filling placeholder.

The previously rejected generic six-output/unsupported-claims/source-check story
is a negative selection example, not a forbidden-topic keyword filter. The
database work-window episode is a positive specificity example: request
validation and configured-window checks must not be rewritten as knowledge that
an actual queue job was due. Endpoint observations do not prove uninterrupted
sleep, measured savings, Free-plan sufficiency or publication success.

## Explicit internal hold

Story Miner, Strategist, Writer and Platform Adapter can begin an artifact with:

    EDITORIAL HOLD: needs_source
    State the missing cleared story detail.

or:

    EDITORIAL HOLD: needs_revision
    State the concrete editorial correction.

Critic keeps the existing strict JSON schema and places that marker at the start
of its existing `Proposed advice:` value. A transparently manual Critic assessment
may use the same marker in its first line while retaining the ordinary factual
critique sections. Do not claim a manual assessment was a model rerun.

The hold is stored in the ordinary immutable artifact bundle, so it is bound to
the same current review token and history. It blocks content approval, combined
publication planning, publication and media approval checks. Factual wording
decisions cannot waive it. Correcting the saved artifact creates a new version;
old approvals remain historical and fresh owner approval is still required.

There is no new API, migration, model, paid rerun, schedule change, source grant,
automatic editorial approval or quality score. Unheld drafts remain
`editorial_review_required`, not quality-passed. The dashboard presents this
separately from factual findings. Existing v3 evidence comparisons and privacy
guards are unchanged; explicit holds add a separate approval prerequisite.

GitHub skill guidance remains selective prompt adaptation, not model training.
`workflow.ts` appends role guidance and the editorial contract to each request;
all bytes use the existing reservation accounting and input/output limits.
Attribution and MIT notices remain in `THIRD_PARTY_NOTICES.md` and `third_party/`.

Offline tests establish prompt construction, hold handling, preserved guards and
version-bound owner control. They do not establish future model compliance or
content quality. A new real dashboard draft still needs editorial and factual
review; manual drafting must not be reported as an autonomous pipeline success.
